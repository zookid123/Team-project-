# 로그라이크 던전 RPG — 교수님 질의응답(Q&A) 준비 가이드

이 문서는 `presentation.txt`의 평가 기준을 바탕으로, 프로젝트의 기술적 결정(ADR)과 아키텍처를 근거로 작성된 예상 질문 및 모범 답안입니다. 발표 시 이 내용을 참고하여 답변하시기 바랍니다.

---

## 1. 비전 및 문제 정의 (Vision & Problem Definition)

**Q: 이 앱의 핵심 비전은 무엇이며, 기존 자동전투 게임과 무엇이 다른가요?**
**A:** 저희 앱의 비전은 "자동전투로 진행되지만 플레이어의 판단이 결과를 결정하는 게임"입니다. 기존 자동전투 게임들이 단순 방치형(Idle)에 가까워 지루함을 유발하는 문제를 해결하기 위해, 전투 중 실시간 '개입 포인트(스킬 발동, 타겟 지정)'를 설계했습니다. 이를 통해 자동의 편의성과 로그라이크의 전략적 재미를 동시에 확보하고자 했습니다.

**Q: 정의하신 세 가지 문제(P1~P3) 중 가장 중요하게 생각한 것은 무엇인가요?**
**A:** P1인 '자동전투의 지루함'입니다. 이를 해결하기 위해 단순 구경이 아닌, 플레이어가 적절한 타이밍에 스킬을 써야만 클리어할 수 있는 난이도 밸런싱과 개입 시스템을 최우선으로 구현했습니다.

## 2. 기술적 의사결정 기록 (ADR — Architecture Decision Records)

> **교수님 필수 질문 대비: ADR의 개념과 각 항목별 결정 이유를 명확히 숙지하세요.**

**Q: ADR(Architecture Decision Record)이 무엇이며, 왜 작성했나요?**
**A:** ADR은 프로젝트의 중요한 기술적 결정사항과 그 결정의 배경, 대안, 결과 등을 기록한 문서입니다. 시간이 흐른 뒤에도 '왜 이 기술을 선택했는지'에 대한 맥락을 유지하고, 팀원 간의 의존성 및 기술적 방향성을 일치시키기 위해 작성했습니다. 저희 팀은 총 3개의 핵심 ADR을 관리하고 있습니다.

**Q: [ADR-0001] 모바일 프레임워크로 Flutter를 선택한 구체적인 이유는?**
**A:** 
- **배경:** 6주 내에 iOS/Android 동시 지원 필수.
- **대안:** 네이티브(Kotlin/Swift), React Native 검토.
- **결정:** Flutter 선택.
- **이유:** 단일 코드베이스로 생산성이 높고, 게임 UI 구현에 필수적인 위젯 시스템이 강력하며, Hot Reload를 통한 빠른 개발 반복이 가능하기 때문입니다.

**Q: [ADR-0002] 상태 관리 라이브러리로 Provider를 선택한 근거는?**
**A:** 
- **배경:** 복잡한 게임 상태(전투 데이터 등)를 여러 화면에서 공유해야 함.
- **대안:** setState, Riverpod, Bloc 검토.
- **결정:** Provider 선택.
- **이유:** Flutter 공식 권장 방식이며 학습 곡선이 낮아 6주 프로젝트에 가장 적합합니다. Riverpod보다 설정이 단순하면서도 현재 규모의 상태 관리를 충분히 수행할 수 있다고 판단했습니다.

**Q: [ADR-0003] 로컬 데이터베이스로 Hive를 선택한 이유는?**
**A:** 
- **배경:** 메타 진행 데이터(영구 해금 등)의 구조화된 저장 필요.
- **대안:** SharedPreferences, SQLite 검토.
- **결정:** Hive 선택.
- **이유:** SharedPreferences는 단순 Key-Value만 가능해 한계가 있고, SQLite는 관계형 쿼리가 필요 없는 본 프로젝트에 너무 무거웠습니다. Hive는 NoSQL 방식으로 성능이 매우 빠르고 Dart 객체를 직접 저장할 수 있어 생산성이 뛰어납니다.

## 3. 앱 구조 및 아키텍처 (App Architecture)

**Q: 앱의 전체적인 구조(레이어)에 대해 설명해 주세요.**
**A:** 저희 앱은 Presentation, ViewModel(Application), Domain, Data 레이어로 구성된 **Clean Architecture 기반의 단방향 레이어 구조**를 따릅니다.
- **Presentation:** UI 위젯 (screens, widgets)
- **ViewModel:** Provider를 활용한 상태 및 흐름 제어
- **Domain:** 순수 게임 로직 (전투 엔진, 던전 생성 알고리즘)
- **Data:** 로컬 DB(Hive) 및 저장소 로직 (SaveRepository)
이 구조를 통해 UI와 게임 로직을 분리하여 유지보수성과 테스트 용이성을 높였습니다.

**Q: 레이어 간의 의존성 규칙은 어떻게 지키고 있나요?**
**A:** Presentation → ViewModel → Domain → Data 순으로만 의존하며, 역방향 의존은 엄격히 금지하고 있습니다. 예를 들어, Data 레이어가 UI나 Domain 레이어를 직접 참조하지 않도록 인터페이스와 의존성 주입을 활용하고 있습니다. (AGENTS.md 준수)

## 4. 빌드 및 배포 (Build & Deploy)

**Q: 빌드와 배포 프로세스는 어떻게 구성되어 있나요?**
**A:** Android는 `flutter build apk` 또는 `appbundle` 명령어를 통해 빌드하며, Firebase App Distribution을 사용하여 테스트 배포를 진행합니다. iOS는 Xcode를 통해 TestFlight에 업로드합니다. 배포 전에는 반드시 `flutter analyze`와 `flutter test`를 통과해야 하는 체크리스트를 운영하고 있습니다. (docs/deploy.md 참고)

**Q: 개발 환경 설정(Setup)을 위해 준비한 것이 있나요?**
**A:** `docs/setup.md`에 '새 사람이 와도 5분 안에 실행할 수 있는 가이드'를 작성했습니다. `flutter doctor` 확인부터 의존성 설치, 실행까지의 과정을 문서화하여 팀원 누구나 동일한 환경에서 개발할 수 있도록 했습니다.

## 5. 테스트 및 품질 관리 (Testing & Quality)

**Q: 어떤 단위 테스트를 진행했나요?**
**A:** 특히 중요한 Domain 레이어의 '자동전투 엔진'과 '던전 생성 알고리즘'에 대해 단위 테스트를 집중적으로 수행했습니다. 예를 들어, 스킬 발동 시 적절한 데미지가 계산되는지, HP가 0이 되었을 때 전투 종료 상태가 정확히 반환되는지 등을 검증했습니다. (test/domain/ 폴더 내 테스트 코드 존재)

**Q: 성능 최적화를 위해 어떤 노력을 했나요?**
**A:** 
1. **리렌더링 최적화:** Provider 사용 시 `context.select` 등을 활용해 필요한 위젯만 다시 그려지도록 설계했습니다.
2. **비동기 처리:** 저장/불러오기 등 I/O 작업은 `Future`와 `async/await`를 통해 UI 스레드 차단 없이 백그라운드에서 처리되도록 했습니다.

## 6. 구현 시행착오 및 개선 (Trial & Error)

**Q: 개발 중 가장 큰 기술적 난관은 무엇이었고 어떻게 해결했나요?**
**A:** (예시 답변) "처음에는 자동전투 로직을 UI 코드와 섞어 작성하여 코드가 매우 복잡해지는 문제가 있었습니다. 이를 해결하기 위해 ADR-0002를 통해 아키텍처를 재설계하고, 모든 게임 로직을 Domain 레이어의 `AutoBattleEngine`으로 분리하여 순수 Dart 코드로 테스트할 수 있게 만들었습니다. 이 과정에서 아키텍처의 중요성을 깊이 체감했습니다."

## 7. 기타 (WBS & Agent)

**Q: WBS 일정 관리는 어떻게 했나요?**
**A:** Must-have(필수), Should-have(권장), Could-have(선택)로 기능을 분류하여 6주 일정을 짰습니다. 현재 Must-have인 자동전투 핵심 로직과 UI 구현을 완료했으며, 일정 내 데모가 가능하도록 버퍼 20%를 포함하여 관리하고 있습니다. (02-wbs.md 참고)

**Q: AI Agent를 개발 과정에서 어떻게 활용했나요?**
**A:** `AGENTS.md`라는 프로젝트 헌법 파일을 작성하여 Agent가 매 턴마다 우리 프로젝트의 아키텍처 원칙과 파일 위치 규칙을 따르도록 강제했습니다. 이를 통해 일관성 있는 코드를 빠르게 생성하고, ADR 기반의 문서화를 자동화하는 데 적극 활용했습니다.
